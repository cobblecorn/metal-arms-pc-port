# Metal Arms cut-content revival audit

Status: source, local US GameCube data, entity/item/weapon registration, and static world placements have now been cross-checked against all 18 entries in The Models Resource's “Unused Content” category. This does not settle the intent of every model variant, rule out content in other platform/region builds, or exclude dynamic mission-script spawns. The game was not launched for this audit. **Sniper runtime status:** the source and port integration are present, but the opt-in spawn is not a valid enemy test yet; the latest run appeared floating and was flung away, while an earlier run asserted/froze and teardown reported active AI resources. See [`enemy-revival-map.md`](enemy-revival-map.md) for the source-backed roster and AI notes. Retail files remain local under `gamedata/` and are not copied into the repository.

## Findings at a glance

The strongest enemy-revival lead is the Mil Sniper. The checkout has its actor, animations, packed bot data, scope dependency, and grapple implementation. Its primary fire constructs damage-bearing tracer shots, and it shares the base bot's targeting, movement, damage, and death paths. The class is registered in the port, but its test spawn is unreliable and no static retail `.wld` placement was found. Enemy aim, cadence, and death behavior remain unverified. Its rifle is actor-owned rather than a normal Glitch inventory weapon; making it a standard inventory weapon is a separate feature.

The Swarmer Queen has a substantial movement/animation prototype, but its bot, animation data, and encounter manager are all disabled with `#if 0`. The manager follows the player over a spherical arena and handles wall/floor transitions. The boss work loop has no active targeting, attack, damage, or phase path; the packed Queen table has only shared bot tables. No static Queen placement was found. Restoring an encounter needs more than enabling its files.

Most other archive entries resolve to visual variants, generic props, or meshes without distinct gameplay registration. The Ripper is already an active weapon; the archive entry has not been proven to be a separate behavior or even a different active model.

### Sniper firing and grapple details

`CBotSniper::_WeaponWork()` fires from the model's `Primary_Fire` bone when `m_fControls_Fire1` is held. It calls `ConstructDamagerData()` and passes the result into `tracer_NewTracer()`, so this is an actual damage path rather than a visual-only laser. The actor receives bot controls after `CBot::ClassHierarchyWork()` performs its shared AI work; actual enemy shot timing/accuracy is still being verified in-game. Reload time and tracer resources are hard-coded/defaulted in the class; the `Sniper`-specific game-data map entry is commented out.

Fire 2 runs a grapple state machine: idle → aim/validate → release-to-fire → hook launch → cable travel → landing or wall cling → release/reload. `CGrapple` owns collision and cable work; `CBotSniper` owns traversal movement, orientation, and animation. The engine callback has been adapted to the current collision API and the ability is now reachable from a `BotSniper` actor. Its useful enemy AI behavior is unknown: existing source only shows the player-control path setting Fire 2, so we should not assume the bot brain will grapple without additional AI logic.

The primary shot belongs to the actor, not the standard weapon inventory. To offer it as a standalone Glitch weapon, a new weapon type would need firing/reload/ammo rules, the rifle mesh/attachment, damage tuning, inventory and save classification, and HUD/reticle prompts. The shorter path to a player-controlled Sniper is possession of this actor; that remains a second step after the enemy test.

### Additional source-backed gaps adjacent to the archive list

- **Ordinary Swarmer:** the class and factory path exist, but `botswarmer.cpp` requests `b_swarmer.csv`, absent from the local US GameCube MST index. Do not equate this ordinary NPC with the disabled Queen.
- **Mining Laser charged burst:** retail `w_laser.csv` rows have 73 fields. The port maps core beam/recharge data, while source comments identify charged-burst fields and particle effects as unimplemented. The ordinary laser remains usable; this is partial retail behavior recovery.
- **Scatter Blaster extras:** retail `w_blaster.csv` rows have 45 fields; the port maps 43 and retains two without behavior. The regular weapon is active, while the extra fields' meaning remains unresolved.

## Suggested revival sequence

1. **Repair the test harness before another gameplay test.** Place the actor from a successful world-surface ray hit and own/destroy it before AI-system teardown; then confirm it renders on the floor, acquires the player, fires and can be damaged/killed. Test whether its inherited AI ever uses grapple controls; if not, add an enemy-only grapple tactic based on level geometry.
2. **Author and validate a real Sniper placement.** The static `.wld` audit found no BotSniper placement, so use a separate test placement first. Confirm AI profile, cover/range, grapple routes, checkpoint/death behavior, and script interactions before any campaign insertion; dynamic scripts and spawn systems were not fully traced.
3. **Add the playable mode.** Build on the same actor's player-index control path after enemy use is sound; verify action-button scope, primary fire, grapple traversal, camera, HUD, and weapons/menu interactions.
4. **Recover the Queen encounter.** Identify or rebuild its sphere arena, remove hard-coded test-only assumptions, implement attacks/damage/phase timing, then restore the disabled bot and encounter manager behind a debug launch first.
5. **Prototype Water/Nuke or Grenade Launcher only if desired.** Start from their asset-only status and define projectile behavior, blast/damage profiles, item/save IDs, pickups, HUD text, and balance data before integrating. Do not treat the active Magma Bomb or ordinary rocket launcher as proof these are already supported.
6. **Triage visual-only assets.** Compare early variants and cross-region resources before creating new classes. Check the European disc specifically for Berserker if available.

## Evidence and limits

- Primary local evidence: `ma/App/ma/botsniper.cpp`, `botsniper_data.cpp`, `grapple.cpp`, `weapon_scope.cpp`, `botswarmerboss.cpp`, `botswarmerboss_data.cpp`, `swarmerbossgame.cpp`, `entity.h/.cpp`, `gameloop.cpp`, `gamedata/mst_index.csv`, and the extracted named GameCube resources.
- External lead list: [The Models Resource — Metal Arms: Glitch in the System (GameCube)](https://models.spriters-resource.com/gamecube/metalarmsglitchinthesystem/). Its category is user-contributed; code and retail data take precedence for revival decisions.
- **Placement audit:** `.wvs` is the GameCube streaming-audio format (`ma/Lib/Fang2/dx/fdx8data.h`, `fdx8audio.cpp`), not a world format. The MST index has 59 `.wld` resources; all 59 static world init blocks were decoded using the layout/conversion paths documented in `ma/Lib/Fang2/fdata.h` and implemented in `port/gcdata.cpp`. The decode validated 16,396 shape records, including 11,556 with embedded GameData. Static data contains 57 `BotBlink` placements but no BotSniper, BotSwarmer/Queen, Berserker, or cut-weapon entity types. `BotBlink` currently maps to `CBotMiner`; the name alone does not prove these are early-Glitch actors. Some entities named `snipergrunt1` are typed as BotGrunt/BotJumper, not BotSniper.
- The placement result is limited to static world init records. It does not rule out runtime/script-created actors, script-level use of generic mesh props, or placements from other regional/platform builds. The workspace has the US GameCube image and extracted data; other platform/region dumps could reveal more.
